# genome-cover-thresholding

## Summary

Zebra-style genome cover thresholding filters false-positive taxonomic hits from shotgun metagenomic alignments by aggregating unique genome coverage across like samples into 'artificially deep' sequencing, then dropping .sam alignments to genomes whose coverage_ratio falls below a user-set cutoff.

## When to use

Use when short shotgun reads spuriously map to short common motifs or transposable elements against a large reference (e.g., Web of Life), creating ambiguous low-coverage false positives that per-sample coverage cannot resolve because shotgun sequencing is shallow.

## When NOT to use

- Input is already an abundance/biom table without alignments — filtering the table directly is explicitly 'not recommended' since it decreases apparent reads instead of redistributing them via Woltka
- Alignments were not generated by bowtie2 or SHOGUN (bowtie2 option), or the reference is not the Web of Life database, which calculate_coverages.py currently requires
- The dataset lacks multiple like samples from similar environments, so the aggregation assumption that true microbes recur across samples (making cover saturate) does not hold

## Inputs

- Directory of .sam alignment files generated by bowtie2 or SHOGUN (bowtie2 alignment option)
- Web of Life (WoL) genome metadata file (databases/WoL/metadata.tsv)
- Coverage .tsv produced by calculate_coverages.py (columns: gotu, covered_length, total_length, coverage_ratio, strain)
- User-set coverage_ratio cutoff (FLOAT, filter_sam.py default 0.1)

## Outputs

- Coverage .tsv from calculate_coverages.py listing per-genome coverage metrics
- One filtered alignment file named <input>_filtered.sam per input .sam, written to a new output directory
- Record of each reference genome retained or dropped at the chosen threshold with its coverage_ratio
- Filtered alignments suitable for regenerating a Woltka biom abundance table

## How to apply

First run calculate_coverages.py over the directory of .sam alignment files (bowtie2 or SHOGUN bowtie2-option alignments) with the Web of Life metadata.tsv to compute aggregated unique coverage per GOTU, where multiple reads over the same genomic position count only once; the output .tsv lists gotu, covered_length, total_length, coverage_ratio (covered_length / total_length), and strain. Choose a coverage_ratio cutoff from that output (filter_sam.py default 0.1; the tiny 5-file test dataset uses 0.0008 because coverages are extremely low). Then run filter_sam.py, which writes one <input>_filtered.sam per input alignment, retaining hits only to genomes whose coverage_ratio meets the cutoff. Rationale: aggregating coverage across like samples from the same environment makes true positives reach higher genome cover while mis-mappings to short motifs stay low, since only unique coverage is counted. Finally feed the filtered alignments to Woltka to regenerate the abundance table rather than filtering the table directly, because filtering the table decreases apparent read counts instead of redistributing reads to other hits.

## Examples

```
python filter_sam.py -i test_data/sample_output.tsv -s test_data/sample_alignments/ -c .0008 -o test_data/filtered_sample_alignments
```

## Evaluation signals

- Each <input>_filtered.sam contains alignments only to genomes whose coverage_ratio in the calculate_coverages.py .tsv is at or above the chosen cutoff (e.g., 0.0008 in the test example)
- Output directory contains exactly one *_filtered.sam file per input .sam alignment file
- coverage_ratio values in the coverage .tsv equal covered_length / total_length for each GOTU (e.g., G001578205: 20963 / 3878815 ≈ 0.005404)
- Only unique genomic positions contribute to covered_length — repeated reads over the same locus must not inflate coverage
- The filtered alignments, when passed to Woltka, yield a biom table in which removed false positives are redistributed to other hits rather than lost as read counts

## Limitations

- calculate_coverages.py currently only works with the Web of Life database (https://biocore.github.io/wol/)
- Ambiguous reads overlapping multiple reference genomes create artifacts, a problem that grows as the WoL reference database expands
- A threshold indicates a spurious reference hit or distant relative only on saturated genome cover, not on per-sample genome cover itself; with a tiny dataset coverages are extremely low, forcing cutoffs like 0.0008 instead of the default 0.1
