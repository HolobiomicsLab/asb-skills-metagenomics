# heterozygosity-and-titv-statistics-computation

## Summary

Computes individual-based counts of heterozygous, homozygous-reference, and homozygous-alternative SNPs plus transitions/transversions, and population-based window statistics (MAF, observed and expected heterozygosity), as implemented in the scalepopgen filtering-and-basic-statistics sub-workflow.

## When to use

Use when a filtered biallelic SNP dataset (VCF or PLINK BED) needs per-sample heterozygosity/homozygosity counts, Ti/Tv ratios, or population-level MAF and Ho/He summary statistics in defined genomic windows.

## When NOT to use

- The dataset has not yet passed the filtering sub-workflow — sample filtering must precede site filtering and the paper's validation requires the filtered set to be smaller than the input
- The data are not biallelic SNP genotypes (the pipeline targets biallelic SNP data in VCF or PLINK binary format), e.g. multi-allelic variants or haploid structural variants
- The analysis goal is genetic structure (PCA/ADMIXTURE), phylogeny (TreeMix), or signatures of selection — those are separate scalepopgen sub-workflows

## Inputs

- Filtered PLINK binary genotype files (bed/bim/fam) or chromosome-split, tabix-indexed biallelic SNP VCFs (.vcf.gz + .tbi)
- Sample map file (.map) with two tab-delimited columns: individual IDs and population IDs, no header
- YAML parameter file generated by the scalepopgen CLI specifying filtering and window/statistic options

## Outputs

- Per-individual counts of heterozygous, homozygous-reference, and homozygous-alternative SNPs
- Per-individual transition and transversion counts (Ti/Tv)
- Population-based windowed summary statistics: average MAF, observed heterozygosity, expected heterozygosity
- Compiled summary tables and visualizations produced by the workflow's Python and R scripts

## How to apply

After the scalepopgen sample- and site-filtering stage (sample filtering such as genotype missingness must precede site filtering such as MAF, with optional Plink2 LD pruning), run the basic-statistics processes on the emitted PLINK binary (BED) files. Use Plink v1.9, Plink2, and Vcftools v0.1.16 to count per-individual heterozygous, homozygous-reference, and homozygous-alternative SNPs and to tally transitions versus transversions, and to compute population-level average MAF and observed/expected heterozygosity in user-defined windows, using the sample map file (.map) for population assignments. Parameters come from the YAML parameter file produced by the scalepopgen CLI. Compile the per-individual and per-window statistics into summary tables and plots with the custom Python and R scripts supplied with the workflow. In the paper's cattle case study these statistics were computed on the filtered set of 269 samples (17 breeds) and ~23.4 million SNPs derived from the original 442 samples / ~25 million SNPs.

## Evaluation signals

- The upstream filtered dataset must be smaller than the input in both samples and sites — in the case study, 442 samples/~25 million SNPs reduced to 269 samples (17 breeds) and ~23.4 million SNPs
- Per-individual heterozygous + homozygous-reference + homozygous-alternative SNP counts must be consistent with the filtered SNP total and each individual's genotype missingness after filtering
- Ti counts should exceed Tv counts genome-wide, giving Ti/Tv values well above 1 for quality biallelic SNP data
- Windowed MAF, Ho, and He tables must be keyed by population IDs matching the supplied .map sample map and window coordinates, and He should satisfy H_e >= H_o in the vast majority of windows under Hardy-Weinberg assumptions
- In the paper's results, MAF and observed/expected heterozygosity were highest in Ankole and Wenshan cattle — a reproducible sanity benchmark for cattle data

## Limitations

- The pipeline targets biallelic SNP data only; phasing/imputation quality of input VCFs affects heterozygosity and Ti/Tv estimates
- Filtering order is mandated: site filtering after sample filtering, so statistics computed before correct filtering will differ from pipeline outputs
- Pipeline-specific caveats: the repository README's changelog and Zenodo DOI are placeholders, and detailed tool documentation was still being updated at the time
